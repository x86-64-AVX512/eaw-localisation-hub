# EaW Hub Sync Protocol (EHSP)

Название протокола – **EaW Hub Sync Protocol**, сокращение **EHSP**. Версия приложения `0.8.8F8` и номер протокола **21** независимы. Поля `protocolName` и `protocolAbbreviation` добавлены в `/health`, `synced` и локальный `agentHello` как необязательные метаданные; формат Yjs и критерии совместимости не изменены. Критерий подключения по-прежнему – точное совпадение числового `protocol`.

`mod-contributor` – аддитивная роль: без переводческой роли изменение содержимого допускается только в `localisation/english` и `localisation/replace/english`. Сервер проверяет её перед применением бинарного CRDT, восстановлением истории и изменением конфликтов/проекций. Просмотр, presence, запросы истории/проекций, проверка дискового merge и комментарии/ответы остаются доступны на всех языках. Решения по предложениям, утверждение и применение тикета требуют переводческой роли; контрибьютор управляет только собственными тикетами. Senior translator может создавать `mod-contributor`-инвайты, но не выдавать `admin`. После изменения ролей сервер закрывает существующие document-соединения кодом `1012`, чтобы Agent автоматически получил новую личность при переподключении.

Локальный `GET /api/ui-language` возвращает `preference: auto|ru|en`, `language: ru|en` и `windowsUiCulture`. Авторизованный `POST` сохраняет предпочтение на этом ПК. Маршрут доступен только через loopback с локальным bearer-токеном; чужой Origin отклоняется. Язык интерфейса не изменяет текст документа и не передаётся другим участникам.

Текущая версия сетевого протокола – **21**: обновлять нужно и сервер, и Desktop Agent. Локальный Review объявляет `crdt: "yjs-v1"` в `open`, получает `documentSync` с Yjs-обновлением и отправляет `reviewUpdate` с `documentId` и `updateBase64`. Обычный ввод передаётся сразу, включая отдельные изменения мультикурсора. После переподключения Review повторно отправляет своё CRDT-состояние; повторная доставка идемпотентна. Команды выделения используют необязательное `reviewAnchors`: сериализованные относительные позиции Yjs с идентификатором документа и, для предложений правок, ожидаемым исходным текстом.

Материализация физического файла сохраняет ожидаемые Git-окончания строк и не создаёт дополнительных протокольных сообщений. Протокол 15 введён для серверного прогресса обучения и адресного журнала уведомлений.

Версия протокола: **21**.

В протоколе 21 `disk-merge-check.textPatches` содержит `baseText`, `externalText`, `personalText` как UTF-8 byte patches относительно совместного снимка с указанным `sharedHash`. Патч имеет `positionByte`, `deleteBytes`, `insertBase64`, `encoding: utf8|gzip`; распаковка и итоговый текст ограничены лимитом документа. Успешный `disk-merge-result.textPatches` аналогично содержит `sharedText` и `personalText` относительно того же снимка. При несовпадении хэша патчи не применяются. Ошибка `EAW_MERGE_LIMIT` останавливает автоматический повтор и оставляет файл неизменным.

Результат проверки содержит `mergeRevision`: хэш базы, совместного, личного и внешнего текстов. Переданные `resolutions` действуют только при совпадении `resolutionRevision`. Каждый disk- и canonical-конфликт содержит `conflictId`, привязанный к снимкам и ключу; Review возвращает его через `externalConflictResolve`, Agent – через `git-conflict-resolve`. Устаревшие ответы не разрешают новый конфликт. После ответа сервера Agent повторно проверяет диск; база материализации меняется на итоговую лишь после успешной записи файла.

Начиная с протокола 20 локальный Agent отправляет `disk-merge-check` с базой слияния, внешним и личным текстом, хэшем текущего совместного документа и уже сделанными выборами. Сервер отвечает `disk-merge-result`: либо подтверждёнными конфликтами, либо итоговыми версиями совместного и личного текста. При несовпадении хэша Agent повторяет проверку; до ответа конфликт не показывается, а материализация приостановлена. Повторяющиеся ключи с неизменным количеством вхождений имеют отдельные идентификаторы `occ:N:<key>` в Git- и личных конфликтах. При изменении количества вхождений требуется выбор целой стороны файла.

Начиная с 19, при закрытии последней вкладки Agent посылает `sync-flush` с `requestId`. Сервер обрабатывает его после всех предыдущих сообщений этого соединения, сохраняет состояние комнаты и возвращает `sync-flushed` с тем же ID. Если подтверждение не получено или локальную правку нельзя было отправить из-за состояния Git, Agent сохраняет Yjs-обновление локально и повторяет его при следующем подключении. Подтверждение само по себе не означает доставку правки, которая не была отправлена.

Для персональной материализации Agent отправляет серверу `personal-projection-get`; сервер отвечает `personal-projection` с `subjectAuthorId`, текстом, участниками и конфликтующими авторскими вариантами, в которых участвует выбранный автор. Чужие пересечения больше не показываются пользователю как его собственный конфликт. Запрос может явно выбрать автора, поэтому Review загружает его полный вариант по требованию, не раздувая каждое обычное обновление всеми копиями файла.

Ответ также содержит `gitConflicts` с ключом и хэшем конкретного конфликта. Локальная команда `personalConflictResolve` пересылается как `personal-projection-resolve` с `key`, `choice: mine|git` и `conflictId`; устаревший хэш отклоняется. Неразрешённые личные Git-конфликты блокируют запись режима `mine`, но не предпросмотр и не явный режим `git`. История схемы 5 хранит базу Git, неразрешённые конфликты и раздельную атрибуцию принятых предложений. Старые варианты без базы не записываются автоматически до подтверждения пользователем. Пустой текст ответа является полноценным результатом; отсутствующая готовая проекция не заменяется общим документом.

Локальный WebSocket Review ↔ Agent использует `personalFileMaterialize` для выбора физического содержимого `git|mine`, `personalFileSelectionSet` с `changeId` и бинарным `include` для поключевого состава локального файла и `documentVariantRequest` для просмотра варианта участника. `documentVariantRequest` передаёт `variantEpoch`, который Agent возвращает в `documentVariant`: Review отбрасывает ответ, если за время запроса изменилась общая версия или Git-база. `changeId` имеет вид `key:<localisation-key>`; изменения структуры и отдельных комментариев используют `__file_structure__`. Agent отвечает `documentVariants`, `documentVariant` и `personalFileStatus`; `documentVariants` содержит `localSelections` со строками Git/совместной/локальной версий, видом изменения, строкой-маркером и состоянием `included|excluded|custom`, либо `localSelectionBlocked` для неоднозначного файла с дубликатами. Эти операции не изменяют общий Yjs-текст. Команды 0.8.5F2 `localVersionApply`, `localVersionExit` и `mixedCommitAllow` удалены.

## Быстрый старт документа

Список тикетов загружается параллельно подключению Review и не блокирует синхронизацию документа. Проверки авторизации, доступности тикета, канонического Git blob и конфликтов остаются обязательными. При холодной загрузке комнаты повторно используется уже проверенный сервером Git-снимок. Список изменённых файлов между старым и новым Git HEAD может догружаться после `synced` отдельным существующим `git-status`; устаревший ответ не применяется к изменившейся комнате или конфликту.

Agent вычисляет state vector из начального серверного Yjs update, отдельно от своего объединённого состояния, и отправляет обратно только недостающие структуры. Неподтверждённые удаления передаются даже при совпадении state vectors. Уже доставленная восстановленная правка посылается как минимальный no-op и по-прежнему завершается через `sync-flush`, чтобы безопасно удалить recovery-файл.

Локальный Review объявляет `variants: "compact-v1"` вместе с `crdt: "yjs-v1"`. После `documentSync` Agent не дублирует совместный текст в `sharedBase64`. Если личный текст точно совпадает с Git, `mineFromGit: true` ссылается на `gitBase64` текущего сообщения либо на ранее полученную Git-версию, но никогда на оптимистический текст редактора. Личные патчи сохраняют проверку `mineBaseRevision`. Клиенты без этой возможности получают прежние полные варианты. `documentVariantsRequest` сбрасывает кэш передачи вариантов и восстанавливает полный необходимый снимок. Номер серверного протокола не меняется.

## Аудит и обновление каталога F3

`GET /api/admin/audit` требует management-сессию аккаунта с ролью `admin`; `/api/management/audit` не существует. Параметры: `actor` (имя или ID), `action` (префикс), `from`, `to` (UTC ISO), `before` (курсор), `limit` (до 200). Ответ содержит `records` и `nextCursor`. Журнал хранится отдельно в `audit/`, неизменяемыми записями с ID операции, автором, временем и исходом `started|completed|failed`. Для удаления `started` записывается до операции; отсутствие финального исхода означает неизвестный результат после прерывания. Содержимое ограничено идентификаторами, метаданными, короткими фрагментами и хэшами; пароли, токены и коды не записываются. API удаления журнала и восстановления удалённых объектов нет.

После сохранения каталога сервер рассылает `tickets-changed` с `revision` всем открытым комнатам. Agent передаёт Review `ticketCatalogChanged`. `GET /api/tickets/revision` служит резервной проверкой; `GET /api/tickets` также содержит `revision`.

## Тикеты

Авторизованные HTTP-маршруты `GET/POST /api/tickets`, `GET/PATCH/DELETE /api/tickets/:id` и операции `snapshot`, `apply`, `rebase`, `archive`, `files`, `conflict` управляют полным жизненным циклом тикета. Применение и rebase передают хэши ожидаемых ревизий всех файлов; сервер сначала проверяет весь набор и только затем меняет CRDT-комнаты. Команда локального Review `open` может содержать опциональный `ticketId`; Agent преобразует его в документ `ticket-<uuid>:<relative-path>`. Сервер допускает такой WebSocket namespace только для существующего тикета и файла из его списка.

Локальный HTTP API Review также предоставляет `POST /api/key-replacements/preview|apply`, `GET /api/tickets/:id/diff` и `POST /api/english-open`. Эти маршруты доступны только с временным bearer-токеном loopback-сессии Agent. Пакетное применение обязано повторно сверить SHA-256 каждого затронутого файла. Английский снимок открывается только для чтения и не создаёт серверную CRDT-комнату.

Орфография использует авторизованные `GET /api/spelling/dictionary`, `GET /api/spelling/words` и `PUT /api/spelling/words`. Первый маршрут возвращает базовый Hunspell и компактный расширенный индекс, второй – единый словарь команды, третий добавляет в него слово от любого вошедшего участника. Маршрутов для отправки проверяемого текста нет: файл проверяет локальный worker Review. Agent кэширует неизменяемую базу на время сеанса, но всегда получает актуальный общий список.

Версия протокола: `20`. Формат пока внутренний и может несовместимо изменяться до стабильного релиза.

## Review ↔ Agent

Транспорт: локальный WebSocket на `127.0.0.1`. Review подключается с capability-token из защищённого state-каталога Agent; сервер проверяет `Host`, `Origin` и допустимый путь файла. Каждое текстовое сообщение – один JSON-объект.

Review отправляет `open` с абсолютным путём и исходным текстом, `activate`/`deactivate`/`close` для жизненного цикла документа, `reviewUpdate` с обновлениями Yjs и `cursor` для присутствия. Остальные команды: брони (`reservationCreate`, `reservationDeleteAt`, `reservationDelete`), комментарии и предложения, `undo`/`redo`, `externalConflictResolve`, операции персонального файла и просмотра авторских вариантов. Полный перечень и ограничения полей определены в `packages/shared/src/protocol-schema.mts`.

Agent отправляет `agentHello`, `documentStatus`, `documentReady`, `documentSync`, `replace`, `workspaceChanged`, состояние присутствия, броней, комментариев, предложений, Git-конфликтов и персонального файла. `reviewBatchStart`/`reviewBatchEnd` ограничивают атомарный снимок обсуждений и предложений. При потере соединения Review переподключается к тому же loopback endpoint и повторяет своё CRDT-состояние. Координаты команд выделения передаются в байтах UTF-8; `reviewAnchors` защищают их от сдвига текста.

## Agent ↔ сервер

Запись истории с `reason: suggestion` использует `author*` для принявшего изменение пользователя и отдельные `suggestionAuthor*`/`suggestionId` для создателя предложения. Это разделение одновременно определяет подписи Review и владельца изменения в персональных проекциях.

Для обычной комнаты Agent передаёт query-параметры `document`, `head` и `blob`: полный SHA локального коммита и blob SHA конкретного файла в локальном `HEAD`. `synced.git` и `git-status` содержат локальные/канонические commit и blob, ветку, причину статуса, время проверки и ограниченный список localisation-файлов, изменённых во всём диапазоне от локального `HEAD` до канонического. `branch-outdated` только предупреждает о новом commit; `file-outdated` запрещает изменяющие команды лишь для комнаты изменившегося файла. Коммит вне поддерживаемых localisation-папок не блокирует документы. После Pull Agent замечает новый `HEAD`, пересчитывает blob и автоматически переподключает комнаты.

Если серверное обновление Git и совместный документ меняют один ключ по-разному, сервер отправляет `conflict` и список ключей. `git-conflict-resolve` принимает выбор `collaborative` либо `external` для одного ключа; после разрешения всего набора сервер завершает трёхстороннее слияние. До этого комната остаётся read-only. Agent до блокировки сохраняет незакоммиченный локальный файл в собственном каталоге `git-recovery`.

`GET /api/git/head?branch=...` возвращает авторизованному Agent каноническую вершину и защищает пакетную замену по ключам. Серверная Git-база и совместные комнаты охватывают `localisation/russian`, `localisation/english` и `localisation/replace`; `canSeed` остаётся для режима без канонического источника и изолированных сценариев.

Транспорт: один WebSocket на совместный документ. Идентификатор документа передаётся query-параметром `document`, а токен сессии – заголовком `Authorization: Bearer …`. Для удалённого сервера этот канал обязан идти через TLS (`wss://`).

Бинарные сообщения содержат Yjs updates. JSON-сообщения обслуживают подтверждение синхронизации, присутствие, брони, комментарии, предложения правок и сообщения об ошибках. Сервер хранит последнее presence-состояние активных соединений только в памяти и передаёт его новым участникам комнаты. Не обновлённый за 45 секунд presence удаляется; служебное время heartbeat не записывается, не отправляется клиентам и не журналируется. Границы броней, комментариев и предложений кодируются как Yjs RelativePosition в Base64. При пустой серверной комнате только один Agent получает право `canSeed`, чтобы одновременное подключение двух одинаковых локальных файлов не создало две копии исходного текста в CRDT.

`synced` и последующие сообщения `history` содержат только метаданные версий и идентификатор текущей вершины. Review запрашивает содержимое конкретной версии командой `history-get`; сервер отвечает `history-version`. Команда `history-restore` обязана передать выбранный ID и увиденный клиентом `headId`. Несовпадение вершины отклоняет восстановление как устаревшее. Успешное восстановление выполняется серверной Yjs-транзакцией и создаёт новую запись `restore`, не перематывая и не удаляя историю.

В `synced.identity` сервер возвращает идентификатор, каноническое имя и массив ролей вошедшего пользователя. Поля имени и автора в отправленных Agent presence/бронях не считаются доверенными и заменяются серверной личностью. Presence-сообщение проходит через белый список полей и не может протащить на сервер `userId`, путь, время либо произвольные метаданные. Код закрытия WebSocket `1008` означает отказ авторизации или отзыв доступа; Agent останавливает переподключение до нового входа.

HTTP API включает публичные `GET /health`, регистрацию `POST /api/auth/redeem`, вход `POST /api/auth/login` и одноразовое восстановление `POST /api/auth/password/recover`. Авторизованные методы: `GET /api/auth/me`, `POST /api/auth/logout`, `POST /api/auth/password/change`, а также двухфазные `POST /api/auth/recovery/issue|confirm|discard`. `POST /api/management/session` требует обычный токен аккаунта `admin` либо `senior translator` и пароль, после чего возвращает отдельный десятиминутный токен только в памяти клиента; `DELETE /api/management/session` отзывает его. Маршруты `/api/admin/*` сохранены как совместимый alias. Изменение ролей, приглашения, состояния аккаунта, удаление, разрешение recovery и временный пароль требуют сессию не старше двух минут. `POST /api/management/users/:id/enable|disable` меняет доступ без удаления, а `DELETE /api/management/users/:id` удаляет аккаунт. `GET /api/management/invites` возвращает роли, лимит, число и остаток активаций и статус; активный код отзывается отдельной командой. Открытый код возвращается только при создании. `POST /api/admin/backup-token` выдаёт отдельный persisted-токен, который принимается только `GET /api/admin/backup` и предназначен для планировщика. Открытый код восстановления управляющему не возвращается. Тела ограничены 64 КиБ; ответы авторизации имеют `Cache-Control: no-store`.

Пароли имеют длину 12–256 символов и проверяются по индивидуально посоленному scrypt-хешу. Неуспешный вход отвечает одной и той же ошибкой для неизвестного имени и неверного пароля. Ограничения повторов разделены по аккаунту и краткоживущему HMAC источника; они существуют только в памяти и не образуют журнал IP. Сессия администратора живёт до 7 дней, обычная – до 30 дней; на аккаунт допускается не более восьми сессий. Изменение пароля отзывает все сессии пользователя, кроме текущей, а сброс – все прежние сессии и сам одноразовый код.

## Ограничения протокола

В протоколе 19 уже есть независимые авторские проекции с разрешением личных Git-конфликтов, аутентифицированная личность, серверный прогресс модульного обучения и адресный журнал событий для локальных уведомлений, отдельная повторно подтверждённая management-сессия, ограничения `senior translator`, отключение аккаунтов, история и отзыв приглашений, защищённое loopback-соединение Review с Agent, пофайловая проверка Git, горячая смена workspace, данные для локального conflict diff, жизненный цикл открытых документов, CRDT-обновления Review, несколько ролей, комментарии и предложения правок. Ещё нет покомнатных разрешений, распределённого rate limiting, подтверждения доставки presence-сообщений, сжатия, negotiation возможностей и совместимости между разными версиями протокола. Это сырая ранняя бета-версия, которую следует публиковать только через корректно настроенный TLS reverse proxy.
