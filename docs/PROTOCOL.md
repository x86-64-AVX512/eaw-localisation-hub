# Протокол 0.8.6F4

F4 сохраняет сетевой протокол **14**: обнаружение Git и защита от ложной ветки `unknown` полностью локальны для Desktop Agent. Локальное IPC-сообщение конфликта и команда его разрешения сохраняют необязательное поле `source` (`disk` либо `canonical`), чтобы Agent не смешивал конфликт рабочего файла с серверным Git-конфликтом. Старое сообщение без поля маршрутизируется совместимо по имеющемуся локальному состоянию. Git-история передаётся только через защищённый loopback HTTP Review: endpoint diff принимает две независимые точки `from` и `to` (либо совместимый старый `commit → HEAD`) и не добавляет серверных сообщений.

Материализация физического файла сохраняет ожидаемые Git-окончания строк и не создаёт протокольных сообщений: исправление полностью локально для Agent, поэтому версия протокола остаётся 14.

Версия протокола: **14**.

Для персональной материализации Agent отправляет серверу `personal-projection-get`; сервер отвечает `personal-projection` с `subjectAuthorId`, текстом, участниками и конфликтующими авторскими вариантами. Запрос может явно выбрать автора, поэтому Review загружает его полный вариант по требованию, не раздувая каждое обычное обновление всеми копиями файла.

Локальный IPC использует `personalFileMaterialize` для выбора физического содержимого `git|mine` и `documentVariantRequest` для просмотра варианта участника. Agent отвечает `documentVariants`, `documentVariant` и `personalFileStatus`. Эти операции не изменяют общий Yjs-текст. Команды 0.8.5F2 `localVersionApply`, `localVersionExit` и `mixedCommitAllow` удалены.

## Тикеты

Авторизованные HTTP-маршруты `GET/POST /api/tickets`, `GET/PATCH/DELETE /api/tickets/:id` и операции `snapshot`, `apply`, `rebase`, `archive`, `files`, `conflict` управляют полным жизненным циклом тикета. Применение и rebase передают хэши ожидаемых ревизий всех файлов; сервер сначала проверяет весь набор и только затем меняет CRDT-комнаты. Команда локального Review `open` может содержать опциональный `ticketId`; Agent преобразует его в документ `ticket-<uuid>:<relative-path>`. Сервер допускает такой WebSocket namespace только для существующего тикета и файла из его списка.

Локальный HTTP API Review также предоставляет `POST /api/key-replacements/preview|apply`, `GET /api/tickets/:id/diff` и `POST /api/english-open`. Эти маршруты доступны только с временным bearer-токеном loopback-сессии Agent. Пакетное применение обязано повторно сверить SHA-256 каждого затронутого файла. Английский снимок открывается только для чтения и не создаёт серверную CRDT-комнату.

Версия протокола: `14`. Формат пока внутренний и может несовместимо изменяться до стабильного релиза.

## Плагин ↔ Agent

Транспорт: Windows Named Pipe со случайно производным именем. Каждое сообщение — один JSON-объект в отдельной строке. Перед рабочими командами Agent присылает `ipcChallenge` с HMAC-доказательством, после чего плагин отвечает собственным HMAC-доказательством. Плагин начинает отправлять события документа только после ответного `agentHello`; очередь прежнего соединения при переподключении отбрасывается. Общий локальный секрет хранится в Windows Credential Manager и по pipe не передаётся.

Плагин отправляет:

- `hello` — идентификатор экземпляра, версия протокола и ответ на IPC challenge;
- `open` — абсолютный путь и полный текст в Base64;
- `activate`, `deactivate` — единственная активная вкладка экземпляра и снятие её presence без остановки фоновой синхронизации;
- `close` — окончательное закрытие буфера и освобождение его локального наблюдателя/соединения;
- `snapshot` — полный снимок изменившегося буфера в Base64; Agent сводит его к одной минимальной замене;
- `edit` — позиция, длина удаления и вставка в Base64;
- `cursor` — каретка и якорь выделения активной вкладки; неизменившаяся позиция повторяется раз в 10 секунд как heartbeat;
- `reservationCreate` — границы и выбранные `assigneeId`, `assignee`, `assigneeColor`; в защищённом режиме сервер доверяет только ID и сам подставляет канонические имя и цвет;
- `reservationDeleteAt`;
- `reservationDelete` — удаление выбранной в панели брони по идентификатору;
- `commentCreate`, `commentReply`, `commentStatus`, `commentDelete` — ветки комментариев к устойчивому диапазону;
- `suggestionCreate`, `suggestionReply`, `suggestionAccept`, `suggestionRevert`, `suggestionReject`, `suggestionDelete` — предлагаемые замены, обратимое принятие и обсуждение;
- `externalConflictResolve` — выбор совместного или дискового варианта конфликтующего ключа;
- `undo`, `redo`;
- `avatarSet`, `avatarDelete` — установка обработанного WebP-аватара текущего пользователя или возврат к инициалам.
- `personalFileMaterialize` — записать в физический файл чистый Git либо Git с изменениями текущего автора;
- `documentVariantRequest` — запросить read-only проекцию выбранного участника.

Agent отправляет:

- `agentHello`;
- `documentStatus`, `documentReady` — состояние подключения документа к серверу;
- `saveRequested` — запрос материализовать согласованный буфер в локальный файл;
- `externalConflictReset`, `externalConflict` — актуальный набор конфликтов Git для панели; конфликт также несёт исходный, совместный и внешний фрагменты для локального Monaco diff;
- `workspaceChanged` — фазы `switching` и `ready` горячей смены Git-ветки без перезапуска клиентов;
- `replace` — минимальная единичная замена для сведения локального буфера с CRDT;
- `reservationTargetReset`, `reservationTarget` — минимальный справочник допустимых владельцев брони (`id`, `displayName`, `color`);
- `reservationReset`, `reservation` — активная бронь содержит отдельно владельца (`assigneeId`, `assignee`) и создателя (`createdById`, `createdBy`);
- `commentReset`, `commentThread`, `commentMessage` — актуальные комментарии, канонический цвет автора, статус, разрешённый диапазон и сообщения с собственными цветами авторов;
- `suggestionReset`, `suggestion`, `suggestionMessage` — исходный/предложенный текст, канонический цвет автора, решение, диапазон и обсуждение;
- `reviewBatchStart`, `reviewBatchEnd` — границы атомарного снимка комментариев и предложений для Review; Legacy-плагину эти два служебных сообщения не отправляются;
- `presenceReset`, `presence`;
- `notice`, `error`.
- `documentVariants`, `documentVariant`, `personalFileStatus` — общая/Git/собственная версии, загруженный по требованию вариант автора и состояние физического файла.

Позиции этого канала — смещения в байтах UTF-8, как в Scintilla.

## Agent ↔ сервер

Для обычной комнаты Agent передаёт query-параметры `document`, `head` и `blob`: полный SHA локального коммита и blob SHA конкретного файла в локальном `HEAD`. `synced.git` и `git-status` содержат локальные/канонические commit и blob, ветку, причину статуса, время проверки и ограниченный список localisation-файлов, изменённых во всём диапазоне от локального `HEAD` до канонического. `branch-outdated` только предупреждает о новом commit; `file-outdated` запрещает изменяющие команды лишь для комнаты изменившегося файла. Коммит вне поддерживаемых localisation-папок не блокирует документы. После Pull Agent замечает новый `HEAD`, пересчитывает blob и автоматически переподключает комнаты.

Если серверное обновление Git и совместный документ меняют один ключ по-разному, сервер отправляет `conflict` и список ключей. `git-conflict-resolve` принимает выбор `collaborative` либо `external` для одного ключа; после разрешения всего набора сервер завершает трёхстороннее слияние. До этого комната остаётся read-only. Agent до блокировки сохраняет незакоммиченный локальный файл в собственном каталоге `git-recovery`.

`GET /api/git/head?branch=...` возвращает авторизованному Agent каноническую вершину и защищает пакетную замену по ключам. Серверная Git-база и совместные комнаты охватывают `localisation/russian`, `localisation/english` и `localisation/replace`; `canSeed` остаётся для режима без канонического источника и изолированных сценариев.

Транспорт: один WebSocket на совместный документ. Идентификатор документа передаётся query-параметром `document`, а токен сессии — заголовком `Authorization: Bearer …`. Для удалённого сервера этот канал обязан идти через TLS (`wss://`).

Бинарные сообщения содержат Yjs updates. JSON-сообщения обслуживают подтверждение синхронизации, присутствие, брони, комментарии, предложения правок и сообщения об ошибках. Современный Agent агрегирует Legacy-плагин и Review в один стабильный presence-ID на документ, отдавая приоритет активному Review; это не позволяет одному пользователю появляться в комнате дважды из-за двух локальных интерфейсов. Сервер хранит последнее presence-состояние активных соединений только в памяти и передаёт его новым участникам комнаты. Не обновлённый за 45 секунд presence удаляется; служебное время heartbeat не записывается, не отправляется клиентам и не журналируется. Границы броней, комментариев и предложений кодируются как Yjs RelativePosition в Base64. При пустой серверной комнате только один Agent получает право `canSeed`, чтобы одновременное подключение двух одинаковых локальных файлов не создало две копии исходного текста в CRDT.

`synced` и последующие сообщения `history` содержат только метаданные версий и идентификатор текущей вершины. Review запрашивает содержимое конкретной версии командой `history-get`; сервер отвечает `history-version`. Команда `history-restore` обязана передать выбранный ID и увиденный клиентом `headId`. Несовпадение вершины отклоняет восстановление как устаревшее. Успешное восстановление выполняется серверной Yjs-транзакцией и создаёт новую запись `restore`, не перематывая и не удаляя историю.

В `synced.identity` сервер возвращает идентификатор, каноническое имя и массив ролей вошедшего пользователя. Поля имени и автора в отправленных Agent presence/бронях не считаются доверенными и заменяются серверной личностью. Presence-сообщение проходит через белый список полей и не может протащить на сервер `userId`, путь, время либо произвольные метаданные. Код закрытия WebSocket `1008` означает отказ авторизации или отзыв доступа; Agent останавливает переподключение до нового входа.

HTTP API включает публичные `GET /health`, регистрацию `POST /api/auth/redeem`, вход `POST /api/auth/login` и одноразовое восстановление `POST /api/auth/password/recover`. Авторизованные методы: `GET /api/auth/me`, `POST /api/auth/logout`, `POST /api/auth/password/change`, а также двухфазные `POST /api/auth/recovery/issue|confirm|discard`. `POST /api/management/session` требует обычный токен аккаунта `admin` либо `senior translator` и пароль, после чего возвращает отдельный десятиминутный токен только в памяти клиента; `DELETE /api/management/session` отзывает его. Маршруты `/api/admin/*` сохранены как совместимый alias. Изменение ролей, приглашения, состояния аккаунта, удаление, разрешение recovery и временный пароль требуют сессию не старше двух минут. `POST /api/management/users/:id/enable|disable` меняет доступ без удаления, а `DELETE /api/management/users/:id` удаляет аккаунт. `GET /api/management/invites` возвращает роли, лимит, число и остаток активаций и статус; активный код отзывается отдельной командой. Открытый код возвращается только при создании. `POST /api/admin/backup-token` выдаёт отдельный persisted-токен, который принимается только `GET /api/admin/backup` и предназначен для планировщика. Открытый код восстановления управляющему не возвращается. Тела ограничены 64 КиБ; ответы авторизации имеют `Cache-Control: no-store`.

Пароли имеют длину 12–256 символов и проверяются по индивидуально посоленному scrypt-хешу. Неуспешный вход отвечает одной и той же ошибкой для неизвестного имени и неверного пароля. Ограничения повторов разделены по аккаунту и краткоживущему HMAC источника; они существуют только в памяти и не образуют журнал IP. Сессия администратора живёт до 7 дней, обычная — до 30 дней; на аккаунт допускается не более восьми сессий. Изменение пароля отзывает все сессии пользователя, кроме текущей, а сброс — все прежние сессии и сам одноразовый код.

## Ограничения протокола

В протоколе 14 уже есть независимые авторские проекции, аутентифицированная личность, отдельная повторно подтверждённая management-сессия, ограничения `senior translator`, отключение аккаунтов, история и отзыв приглашений, взаимная аутентификация локального IPC, пофайловая проверка Git, горячая смена workspace, данные для локального conflict diff, lifecycle активной вкладки, пакетные снимки Review, несколько ролей, комментарии и предложения правок. Ещё нет покомнатных разрешений, распределённого rate limiting, подтверждения доставки presence-сообщений, сжатия, negotiation возможностей и совместимости между разными версиями протокола. Версия остаётся альфа-версией и должна публиковаться только через корректно настроенный TLS reverse proxy.
