# Архитектура прототипа 0.8.7F1

## Изменения 0.8.7F1

`git-executable.mjs` централизует все локальные Git-вызовы Agent и на Windows ищет как системный Git, так и Git, встроенный в последнюю установленную версию GitHub Desktop. Отсутствующий результат определения ветки считается временной ошибкой наблюдения, а не новым workspace; переход запускается только после двух последовательных успешных наблюдений одного имени ветки.

Отдельный Windows-deployer формирует минимальный серверный пакет без runtime-данных, подключается по SSH/SFTP с закреплением host key, проверяет SHA-256 уже загруженного архива и обновляет Compose-проект. Перед заменой сохраняется откатная копия кода; неуспешная сборка, запуск или `/health` возвращают предыдущую серверную версию. Постоянный Docker volume, `.env` и каталог внешних резервных копий не заменяются.

## Изменения 0.8.6F3

Legacy-плагин загружает сохраняемый флаг `LegacyIntegration/Enabled` из каталога конфигурации плагинов Notepad++. При отсутствии настройки значение равно `false`: транспорт, таймер, Scintilla-subclass, dock-панель, индикаторы и обработка изменений не создаются. Единственная постоянно доступная команда включает интеграцию на горячую; отключение останавливает IPC, очищает визуальное состояние и возвращает управление документом самому Notepad++.

Команда открытия Review остаётся доступной в спящем режиме. По требованию она поднимает только защищённый IPC-транспорт до Agent и отправляет `reviewOpen`; Agent проверяет принадлежность пути поддерживаемому localisation-дереву и открывает Review без требования предварительного `open`. Scintilla-subclass, таймер наблюдения, индикаторы и публикация текста или курсора при этом не включаются.

`git-file-history.mjs` выполняет только локальные Git-команды с массивом аргументов и проверенным путём внутри поддерживаемых localisation-папок. История следует переименованиям, отдаётся Review страницами и позволяет независимо прочитать две выбранные точки истории либо текущий `HEAD`. Monaco Diff Editor вычисляет визуальное сравнение и скрывает неизменённые области; сервер совместной работы в этом потоке не участвует.

Конфликты локального дискового слияния и канонического Git имеют источники `disk` и `canonical`. Сброс удаляет только свой источник, а разрешение маршрутизируется в соответствующий обработчик. Завершённое локальное разрешение обновляет базу и очищает карточки у всех Plugin/Review-клиентов этого пути. Начало горячей смены workspace безусловно удаляет прежнее визуальное состояние, а прочитанный checkout нормализуется к внутреннему `LF`.

## Изменения 0.8.6F2

Внутреннее представление наблюдаемого дискового текста нормализуется к `LF`, а защищённая материализация отдельно восстанавливает физический EOL worktree. Для уже открытого `CRLF` сохраняется его формат; если прежняя версия Hub успела записать `LF`, ожидаемый EOL определяется без запуска clean/smudge-фильтров по `.gitattributes`, `core.autocrlf` и `core.eol`. Кэш предпочтений очищается при горячей смене ветки. Перед `truncate` готовые байты сравниваются с текущим файлом, и полностью совпадающий файл не записывается повторно.

## Изменения 0.8.6F1

Серверный Yjs-текст остаётся общей рабочей копией для Review, комментариев, предложений, истории и тикетов, но `DocumentHistory` дополнительно хранит независимую карту изменённых localisation-ключей каждого автора относительно канонического Git-текста. Новый автор не перезаписывает вариант прежнего: изменение одного ключа несколькими людьми образует набор авторских вариантов и явный конфликт.

`personal-document.mjs` запрашивает серверную проекцию `Git HEAD + изменения текущего пользователя`. `document-view.mjs` отдаёт общую версию только Review, а Legacy-плагину – персональную. `review-server.mjs` материализует в настоящий файл репозитория персональную версию; удалённые Yjs updates обновляют общую модель и метаданные, но не записывают чужой текст в Git worktree. Режим материалации (`mine` либо чистый `git`) хранится вне репозитория с привязкой к репозиторию, ветке и пути.

Review может по запросу получить проекцию любого участника и открыть её только для чтения рядом с общей, собственной и Git-версиями. Возврат рабочего файла к Git или `Git + мои` является локальной операцией и не создаёт Yjs update. Устаревший mixed-author pre-commit guard 0.8.5F2 удаляется при запуске Agent; если до него существовал пользовательский hook, Agent восстанавливает сохранённый оригинал.

## Изменения 0.8.5F1

Схема авторизации 5 хранит `enabled` отдельно от существования пользователя. Отключение физически удаляет его обычные и backup-сессии и исключает из каталога участников, но сохраняет учётную запись. Безвозвратное удаление дополнительно анонимизирует ссылки в загруженных и сохранённых комнатах и истории.

Короткая повторно подтверждённая сессия стала management-сессией для `admin` и `senior translator`. Отдельный модуль политики запрещает senior управлять собой, администраторами, ролью `admin` и приглашениями администратора; другие роли, включая новых `senior translator`, разрешены. Экспорт и расписание резервных копий дополнительно требуют `admin` независимо от management-сессии.

Приглашения больше не удаляются после истечения или исчерпания. Persisted-запись хранит только хеш секрета, роли, лимит, число использований, срок и флаг отзыва. Открытый код восстановить из списка невозможно. Статусы `active`, `expired`, `exhausted` и `revoked` вычисляются без журнала персональных действий.

Навигация Review вычисляет все открытые комментарии и правки под нажатой UTF-8 позицией, выбирает сначала самый узкий диапазон и прокручивает независимую правую колонку к карточке по стабильной паре `kind:id`. Повторное нажатие перебирает наложенные сущности.

## Изменения 0.8.4F2

При горячей смене ветки Agent немедленно замораживает локальные клиенты, но откладывает чтение файлов до исчезновения `index.lock` и стабильности пары `HEAD / Git index`. Замена открытого буфера на уже материализованный checkout помечается как синхронизация с диском: Legacy-плагин ставит save point вместо повторной записи файла. Review обновляет контекст ветки по `workspaceChanged` и остаётся read-only до нового `documentReady`.

Каноническая Git-проверка остаётся пофайловой, но список изменений теперь вычисляется за весь диапазон от локального `HEAD` пользователя до канонической вершины, а не только по последнему серверному переходу. Поэтому несколько пропущенных commit не теряют затронутые файлы, а commit вне поддерживаемых localisation-папок не блокирует ни одну комнату. Review показывает предупреждение о новой вершине, список реально изменённых localisation-файлов и красную блокирующую плашку только в изменившемся открытом файле.

Сервер продолжает трёхстороннее слияние `прежняя Git-база / совместный текст / новая Git-база`. Независимые ключи объединяются автоматически; совпавшие конфликты открываются в локальном Monaco diff с двумя сторонами и разрешаются по одному ключу. Agent сохраняет recovery-копию незакоммиченного файла в state-каталоге перед блокировкой.

Серверный модуль `git-branch-cache.mjs` обслуживает отдельные shallow sparse-клоны активных веток публичного репозитория. В кэш входят только `localisation/russian`, `localisation/english` и `localisation/replace`. Обычная комната инициализируется серверным Git-текстом, сохраняет commit и базовый текст в метаданных и при обновлении ветки выполняет трёхстороннее объединение Git-базы, живого CRDT и нового Git-снимка. Тикетные комнаты сохраняют прежнюю изоляцию.

Desktop Agent передаёт полный локальный `HEAD` и blob открытого файла. Несовпадение вершины без изменения этого файла даёт предупреждение, но оставляет комнату доступной для записи; несовпадение blob блокирует только соответствующий файл. Фоновая проверка локального `HEAD` автоматически переподключает комнаты после обновления через GitHub Desktop.

Готовность документа legacy-плагина привязана к текущему поколению открытого буфера: закрытие активного файла немедленно сбрасывает `DocumentState`, текущий и наблюдаемый пути. `SCN_MODIFIED` и контрольный `snapshot` публикуются только после `documentReady` и только при совпадении текущего пути с зарегистрированным. Agent считает преждевременные либо запоздалые `edit`/`snapshot` восстановимой гонкой жизненного цикла и отбрасывает их без пользовательского MessageBox; проверка схемы и обязательный `open` для остальных рабочих команд сохраняются.

Рабочая область Review задаёт единственную ограниченную grid-строку `minmax(0, 1fr)`. Левая колонка имеет `min-height: 0`, собственный вертикальный overflow и несжимаемые секции; при уменьшении WebView2 прокручивается вся колонка, а не содержимое секций поверх соседних блоков.

Legacy-плагин больше не перехватывает `WM_KEYDOWN` для обычных `Ctrl+Z`/`Ctrl+Y`: локальная история снова обрабатывается самим Scintilla и её обратные изменения проходят через существующий поток `SCN_MODIFIED → edit`. Отдельные серверные команды совместной отмены остаются доступны через меню и `Ctrl+Alt+Z`/`Ctrl+Alt+Y`. Входящий `replace` не включается в локальную историю и после применения очищает прежние записи, которые могли стать позиционно недействительными. Review сохраняет компактный Google Docs-вид `зачёркнутый оригинал + цветная замена`; читаемость обеспечивается расширением многобуквенного изменения до границ целого Unicode-слова, а не дополнительными подписями в строке.

Рабочие сообщения legacy-плагина блокируются до полного локального handshake `ipcChallenge → hello → agentHello`. При каждом соединении и подтверждённом challenge исходящая очередь очищается, поэтому события документа от старого pipe не могут обогнать новый `open`. Agent считает преждевременные `activate`, `deactivate`, `cursor` и `close` восстанавливаемыми событиями жизненного цикла и не превращает их в модальную ошибку; команды, меняющие документ, по-прежнему требуют предварительного `open`.

GUI Desktop Agent больше не принимает ручной workspace. Основной запуск всегда использует определённую Git-ветку; параметр `--workspace` остаётся внутренним инструментом лаборатории и диагностики.

Интерактивная администрация отделена от обычной сессии аккаунта. `AdminSessionStore` держит только в памяти хеши десятиминутных admin-токенов, привязанных к исходной пользовательской сессии. Получение требует повторной проверки пароля; операции изменения доступа принимают только сессию не старше двух минут. Admin UI хранит токен в переменной процесса и отзывает при закрытии. Долговременное расписание резервных копий использует отдельный persisted-токен с единственным разрешением на экспорт и не может вызывать остальные административные методы. HTTP-маршруты администрации вынесены в `admin-http.mjs`.

Agent помечает начало и конец полного снимка комментариев и предложений сообщениями `reviewBatchStart`/`reviewBatchEnd` только для Review. Клиент не отображает промежуточные reset-состояния, объединяет запросы отрисовки в один animation frame и сохраняет DOM неизменившихся карточек по стабильному идентификатору и fingerprint. Legacy-плагин продолжает получать прежнюю последовательность сообщений.

Минимальная однобуквенная замена остаётся посимвольной. Если обе стороны заменяют несколько символов внутри одного Unicode-слова, диапазон расширяется до его границ: это не позволяет случайному общему окончанию визуально склеивать разные слова. Вставки, удаления, пунктуация, кавычки и границы строк не расширяются.

Кнопки отмены dialog-форм используют `formnovalidate`, поэтому обязательное название тикета проверяется только при создании, но не при закрытии окна.

Транспорт legacy-плагина ожидает отсутствующий named pipe Desktop Agent с прерываемой задержкой. `WaitNamedPipeW` может немедленно вернуть ошибку, если pipe ещё не создан; явный backoff не позволяет фоновому потоку превращать повторное подключение в busy loop.

Пакетная замена разделена между `key-replacement-panel.js`, чистым разбором `localisation-replace.mjs` и файловой транзакцией `key-replacement-workflow.mjs`. Review никогда не передаёт введённый текст оболочке или Git-команде. Применение использует хэши предпросмотра и останавливается, если файл успел измениться.

Тикетный и исторический интерфейсы создают Monaco Diff Editor на клиенте с `hideUnchangedRegions`. Agent только лениво предоставляет разрешённые снимки; сервер CRDT не вычисляет визуальный diff. Английское окно запускается тем же нативным Review Host, получает снимок только для чтения и синхронизирует прокрутку с русским окном через локальный `BroadcastChannel`, сопоставляя строки по ключам локализации.

Отмена принятой правки остаётся серверной атомарной операцией: сервер проверяет, что принятый текст не изменился, возвращает исходный диапазон и снова открывает правку. Клиентская история решений связывает эту операцию с `Ctrl+Z`/`Ctrl+Y`.

## Тикеты

`TicketStore` хранит метаданные тикетов отдельно от CRDT-комнат: название, описание, базовую Git-ветку, полный commit SHA, файлы, участников и статус. Документ тикета использует namespace `ticket-<uuid>:<relative-path>`, поэтому существующие Yjs, presence, брони, комментарии и предложения изолируются без дублирования их реализации. Agent извлекает начальную версию через `git show <base-commit>:<path>`. Review-клиент не материализует тикет в рабочее дерево.

`TicketService` выполняет серверные операции над всем набором файлов: проверяет хэши тикетных и основных комнат, применяет рассчитанный Agent результат, обновляет базу и физически удаляет тикетные комнаты с историей. `TicketWorkflow` в Agent объединяет базовый Git-текст, текущую совместную основную версию и безопасно прочитанный локальный файл через локализационный трёхсторонний merge. Конфликт любого ключа останавливает всю операцию до записи и переводит тикет в `git_conflict`. Успешное применение обновляет основную CRDT-версию и локальные файлы, но намеренно не создаёт Git-коммит.

В production-конфигурации `GitCommitVerifier` через GitHub Compare API проверяет, что полный базовый SHA существует и является предком выбранной ветки `EaW-Team/equestria_dev`. Проверка имеет восьмисекундный таймаут, часовой ограниченный кэш и закрывается ошибкой при недоступности GitHub. Self-host может сменить репозиторий переменной `EAW_HUB_GITHUB_REPOSITORY`; отсутствие переменной отключает только эту внешнюю проверку для локальной лаборатории и unit-тестов.

`DocumentHistory` хранит для каждой комнаты ограниченную последовательность gzip-снимков текста и публичные метаданные автора/времени. Частые изменения одного автора сворачиваются в одну сессию. Снимки не входят в Yjs и не содержат комментарии, брони или предложения. Восстановление проверяет актуальный `headId`, рассчитывает будущий размер CRDT на копии документа и только затем заменяет текст серверной транзакцией. Оно всегда добавляет новую запись, поэтому является обратимым без разрушительного отката базы.

```text
Notepad++ x64
    │ Windows Named Pipe, NDJSON
    ▼
Desktop Agent пользователя
    ├── loopback HTTP/WebSocket + случайный capability-token
    │       ▼
    │   EaW Review: нативный WebView2 host + Monaco
    │ WSS + Bearer session: Yjs update + JSON metadata
    ▼
Сервер синхронизации и авторизации
    │ atomic write
    ▼
Локальный каталог data/prototype-server
```

## Плагин Notepad++

Плагин является Legacy-клиентом. Его функциональная поверхность заморожена: новые возможности добавляются в EaW Review. Допустимые изменения плагина ограничены исправлениями безопасности, критических дефектов, совместимости протокола и команды запуска Review.

Нативная x64 DLL получает уведомления Scintilla об изменениях текста, позиции курсора, границ выделения, смене и закрытии вкладок. Она передаёт UTF-8 байтовые позиции Agent и применяет пришедшие от него замены. Только текущая активная вкладка публикует presence; фоновые вкладки продолжают получать совместные изменения, не показывая пользователя как присутствующего. Неизменившийся курсор повторяется как heartbeat. Штатный полупрозрачный индикатор Scintilla показывает чужие многострочные выделения под текстом в цветах участников; удалённые каретки рисуются отдельным слоем, поэтому видны на пустой строке и в EOF. Индикаторы Scintilla также показывают мягкие брони и открытые комментарии. Исходник предлагаемой правки зачёркивается стабильным цветом её автора, а новый текст рисуется тем же цветом в отдельном overlay-слое. Режим review размещает до восьми ближайших видимых карточек у правого края редактора, выравнивает их по исходным строкам и соединяет с диапазонами линиями; компактный режим оставляет короткий ghost рядом с диапазоном, раскрывающийся при наведении; скрытый режим отключает внутритекстовую визуализацию. Overlay не меняет Scintilla-буфер и не является частью `.yml`, Yjs-документа или Git diff. Широкая левая док-панель рисует комментарии и предложения отдельными карточками с цветной полосой автора, номером строки, статусом и последним сообщением; карточки отсортированы по позиции и следуют за видимой областью редактора. Цветная подпись участника появляется только при наведении мыши. Обычный щелчок по удалённому участнику переносит к его каретке, а двойной щелчок по карточке – к её диапазону и обсуждению. Плагин не знает пароль, GitHub-токен, адрес репозитория или ветку.

## Desktop Agent

Agent также обслуживает отдельное окно Review. Статические Monaco-ресурсы и WebSocket доступны только через `127.0.0.1`. Случайные порт и capability-token создаются один раз для локального state-каталога и сохраняются с правами текущего пользователя, поэтому уже открытое окно может автоматически переподключиться после перезапуска Agent. Текущий discovery-файл по-прежнему содержит PID и рабочий контекст запуска. HTTP API требует bearer-token, WebSocket – точные token и `Origin`; WebView2 запрещает внешнюю навигацию, новые окна и разрешения.

Web-клиент Review разделён на тонкий координатор `app.js`, панель совместной работы, карточки обсуждений, декорации Monaco, контроллер режимов ввода, историю предложений, профиль аватара и модуль кодировок/безопасных цветов. Архитектурный тест ограничивает размер координатора и крупных UI-модулей. Review реализует всю пользовательскую поверхность Legacy-плагина: presence, брони и делегирование, комментарии, предложения, совместную историю и разрешение внешних Git-конфликтов. Обычный режим Monaco отправляет снимки совместного документа после ввода. В режиме «Правки» клиент вычисляет одну локальную вставку, замену или удаление, возвращает редактор к каноническому тексту и отправляет предложение с UTF-8-границами; исходник меняется только после принятия предложения сервером. Локальная история хранит идентификаторы созданных предложений, поэтому Undo удаляет последнее предложение, а Redo повторно создаёт его; при изменении канонического текста извне потенциально устаревшая redo-ветка очищается.

Аватар подготавливается в Review через Canvas: выполняются квадратное кадрирование, уменьшение до 96×96 и повторное WebP-кодирование без метаданных исходника. Сервер принимает не более 16 КиБ, проверяет canonical base64, RIFF/WebP chunk, размеры 16–256 пикселей и сохраняет результат в учётной записи. Внешние URL не поддерживаются.

Presence Review публикуется при движении курсора и повторяется heartbeat каждые 15 секунд. Agent сводит presence всех локальных интерфейсов одного пользователя в единственный стабильный presence-ID: открытый Review имеет приоритет над Legacy-плагином, а после закрытия Review публикация автоматически возвращается к последней активной вкладке Notepad++. Поэтому одновременный запуск двух интерфейсов не дублирует участника и не оставляет две каретки одного человека. Когда локальных активных интерфейсов не остаётся, Agent немедленно отправляет `offline`; разрыв соединения дополнительно очищается сервером, а потерянное без уведомления состояние удаляется TTL. Для совместимости со старыми Agent сервер по-прежнему умеет принять до восьми presence-ID от одного соединения, привязывает каждый ID к создавшему его сокету и при разрыве удаляет весь набор.

Правки из Monaco после короткого debounce материализуются в локальный `.yml` через уже открытый `r+` handle. До записи Agent канонизирует repository и файл, проверяет containment и совпадение identity открытого handle с каноническим файлом. При внешнем конфликте или смене workspace запись приостанавливается.

Один Agent обслуживает одну локальную копию Git-репозитория и один workspace. Он принимает `.yml` из `localisation/russian`, `localisation/english` и `localisation/replace`, проверяет реальное нахождение файла внутри репозитория, преобразует байтовые позиции Scintilla в UTF-16 позиции Yjs и обратно, держит персональную историю Undo и наблюдает за открытыми файлами на диске.

Окно Agent регистрирует аккаунт по приглашению либо выполняет обычный вход по имени и паролю. Пароль не сохраняется; после запроса поля очищаются. Полученный токен сохраняется как Generic Credential текущего пользователя Windows и передаётся дочернему процессу только через окружение. Плагин не получает ни пароль, ни токен. После аутентификации сервер возвращает каноническое имя и массив ролей. Удалённые пароль и токен разрешено передавать только через TLS; GUI отказывается работать с удалённым `ws://`.

Поле ручного выбора ветки в GUI отсутствует: рабочее пространство определяется текущей Git-веткой.

Для каждого сочетания `абсолютный путь репозитория + workspace + относительный путь файла` Agent сохраняет подтверждённую базу слияния в своём state-каталоге (по умолчанию `%LOCALAPPDATA%\EaWLocalisationHub`). Данные не попадают в рабочее дерево Git. Это позволяет после перезапуска отличить полученные через Pull изменения от правок, уже присутствовавших в совместном документе. Повреждённый либо отсутствующий снимок не приводит к молчаливому выбору стороны: при различающихся версиях создаётся начальный конфликт.

Если `--workspace` не указан, Agent читает текущую ветку командой `git branch --show-current` и наблюдает за Git `HEAD` и `index.lock`. Во время операций Git дисковое слияние откладывается. После переключения ветки старые комнаты закрываются, открытые файлы перечитываются из новой ветки и автоматически подключаются к новым комнатам; Review и Legacy-плагин переходят через фазы read-only и ready без перезапуска. Несохранённый совместный буфер прежней ветки сохраняется в `git-recovery`, а временно отсутствующий в новой ветке файл остаётся учтённым для последующего обратного переключения.

## Сервер

До scrypt действуют отдельные краткоживущие token-bucket лимиты по аккаунту и HMAC источника, а очередь password jobs остаётся глобальным аварийным пределом. Счётчики существуют только в памяти процесса, не содержат исходный IP и не создают персональную историю.

Для каждого идентификатора `workspace:relative/path.yml` сервер держит отдельный Y.Doc. Текст хранится в CRDT, поэтому конкурентные изменения сливаются без блокировки файла. Сервер также держит оперативный список присутствующих и передаёт его вновь подключившимся участникам. Presence имеет 45-секундный TTL и обновляется heartbeat активной вкладки; время последнего heartbeat существует только в памяти. Брони, комментарии и предложения правок сохраняются с границами Yjs RelativePosition. Если позиции больше нельзя разрешить, сущность показывается как orphaned. Предложение содержит исходный текст; сервер атомарно применяет замену только при точном совпадении актуального диапазона, иначе помечает её stale.

Состояние каждой комнаты сохраняется в бинарном Yjs update и минимальных JSON-метаданных броней, комментариев и предложений. Сервер ограничивает размер одного update, состояние комнаты, общий объём загруженных комнат, число подключений и очередь медленных WebSocket-клиентов. Неактивные комнаты после сохранения выгружаются из памяти; объём и число persisted-документов также имеют предел. В метаданные не записываются время сохранения, история удаления или отдельный идентификатор документа. Запись выполняется через временный файл и переименование. Для производственного развёртывания этот формат потребует версионирования и миграций.

Сервер по умолчанию требует авторизацию. Один аккаунт может иметь несколько ролей из `admin`, `senior translator`, `translator`, `trainee-translator`, `translation-editor`. Управление командой доступно `admin` и `senior translator` с ограничениями отдельной серверной политики. Пароль хранится исключительно как индивидуально посоленный memory-hard хеш scrypt (`N=131072`, `r=8`, `p=1`, 32 байта). Одноразовый bootstrap-код создаёт первого администратора. При регистрации выдаётся один 256-битный код восстановления с контрольной суммой. Его открытый текст существует только в ответе пользователя; `auth.json` содержит HMAC-SHA-256, а отдельный `recovery-pepper.key` входит в зашифрованную резервную копию. Выдача двухфазная: код активируется лишь после подтверждённой записи файла, а отменённый или потерянный pending-код аннулируется.

Обычный bearer-токен admin-аккаунта не принимается маршрутами управления: он может только повторно подтвердить пароль и получить короткую административную сессию. Опасные методы дополнительно требуют свежего подтверждения. Отдельный backup-токен проверяется только маршрутом резервного экспорта.

В `auth.json` остаются отображаемые имена, роли, проверочные хеши паролей, кодов восстановления, активных сессий и приглашений. IP, User-Agent, имя устройства, время входа и история отзыва не собираются. После использования кода восстановления аккаунт продолжает работать, но требует администраторского разрешения на новую выдачу; администратор открытый код не видит. Временный пароль отзывает все сессии и не допускается к WebSocket-документам до самостоятельной смены. Выход и отзыв физически удаляют сессию, а удаление аккаунта – сам аккаунт и его сессии. Сервер не печатает секреты в stdout, а Caddy не ведёт access log.

При классической парольной схеме пароль неизбежно кратковременно присутствует в памяти клиента и сервера и идёт внутри TLS. Гарантия этой версии относится к отсутствию парольного текста на диске/в журналах и невозможности восстановить пароль из серверного хеша, а не к невозможному обещанию «никогда не покидает клиент».

Docker-контейнер работает непривилегированным пользователем, имеет read-only root filesystem, лимит 384 МБ и постоянный volume `/data`. Опциональный Caddy завершает TLS; при уже занятом VLESS порте 443 используется существующий reverse proxy. Административный HTTP-экспорт сначала сбрасывает загруженные комнаты на диск, после чего отдаёт только `auth.json` и `documents`. Клиентский скрипт шифрует архив AES-256-GCM до сохранения вне VPS. Восстановление сохраняет прежнее состояние в `.before-restore-*` внутри volume.

## Отношение к Git

Каноническим результатом для Git по-прежнему является рабочая копия конкретного переводчика. В неё материализуются Git-база и только изменения этого переводчика; общая версия и чужие авторские варианты остаются в серверной комнате и локальном виртуальном представлении Review. Коммит и push участник делает лично через GitHub Desktop. Сервер не является Git-сервером и не подменяет авторство коммитов.

При внешнем изменении Agent сравнивает `последний подтверждённый персональный файл / общую версию / новую версию с диска`. Разные ключи объединяются в общей комнате с авторством операции. Если локальный пользователь меняет ключ, уже изменённый другим автором, его полный вариант сохраняется отдельно и требует явного выбора вместо посимвольного CRDT-смешивания. Новая база дискового согласования записывается только после фактической материализации персонального итога.

## Границы исходного кода

Основные entrypoint-файлы только связывают подсистемы. Для Agent отдельно существуют жизненный цикл `DocumentBinding`, команды броней/review, построение представления для плагина и reconciliation с Git-файлом. На сервере отдельно расположены HTTP/WebSocket bootstrap, `DocumentRoom`, реестр и выгрузка комнат, нормализация persisted metadata, протокольные лимиты, модель аккаунтов и хранилище аутентификации.

В нативном плагине отдельно компилируются IPC-криптография, строгий JSON-протокол, Win32/Scintilla interop, lifecycle, модели данных, цвета и слой курсоров/hover-карточек. Главный файл пока сохраняет Win32 dock-panel и диспетчер событий Notepad++, поскольку они используют одно UI-состояние; дальнейшие функции не должны возвращаться в уже выделенные модули.

Тест `architecture.test.mjs` задаёт верхние границы размера координирующих файлов и проверяет наличие выделенных модулей. Это не метрика качества сама по себе, а предохранитель от незаметного возврата к прежним монолитам.
