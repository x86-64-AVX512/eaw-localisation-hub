# Архитектура EaW Localisation Hub 0.8.8F9

Документ описывает текущее устройство системы по подсистемам. Порядок появления изменений и их версии записаны в [CHANGELOG.md](../CHANGELOG.md), правила сетевого обмена – в [PROTOCOL.md](PROTOCOL.md).

## Компоненты и границы доверия

```text
EaW Review: нативный WebView2 host + Monaco
    │ loopback HTTP/WebSocket + capability-token
    ▼
Desktop Agent пользователя ──── локальный Git worktree (GitHub Desktop)
    │ WSS + Bearer session: Yjs update + JSON metadata (EHSP)
    ▼
Сервер синхронизации и авторизации
    │ atomic write
    ▼
Постоянный каталог данных (/data в Docker, data/prototype-server в лаборатории)
```

- **Сервер** хранит совместный Yjs-документ каждого файла, метаданные броней, обсуждений и предложений, авторскую историю, тикеты, учётные записи и журнал аудита. Сервер не является Git-сервером и не подменяет авторство коммитов.
- **Desktop Agent** обслуживает одну локальную копию репозитория пользователя: связывает открытые файлы с серверными комнатами, материализует в worktree личную версию пользователя и раздаёт Review локальный API.
- **Review** – окно редактора. Оно является Yjs-участником, но никогда не получает пароль или серверный bearer-токен и не обращается к серверу напрямую.

Каноническим результатом для Git остаётся рабочая копия конкретного переводчика. В неё материализуются Git-база и изменения только этого переводчика; общая версия и чужие авторские варианты остаются в серверной комнате и в виртуальном представлении Review. Коммит и push участник делает лично через GitHub Desktop.

## Сервер

### Комнаты и CRDT

Для каждого идентификатора `workspace:relative/path.yml` (или `ticket-<uuid>:<path>`) сервер держит отдельный `Y.Doc`. Текст хранится в CRDT, поэтому конкурентные изменения сливаются без блокировки файла. HTTP/WebSocket bootstrap (`main.mjs`), `DocumentRoom`, реестр и выгрузка комнат (`room-registry.mjs`), нормализация persisted metadata (`room-metadata.mjs`), протокольные лимиты и транспорт документа (`document-socket.mts`) разделены по модулям.

Каждое WebSocket-соединение обрабатывает сообщения через последовательную очередь, а у каждой комнаты есть своя очередь операций. Права записи повторно проверяются внутри комнатной очереди и после асинхронной CRDT-валидации. `sync-flush` упорядочен после предыдущих сообщений того же соединения и подтверждается только после сохранения комнаты. При штатном завершении сервер прекращает приём новых сообщений, дожидается поставленных в очередь операций, закрывает соединения и только затем сохраняет комнаты.

Состояние комнаты сохраняется как бинарный Yjs update и минимальные JSON-метаданные. Сервер ограничивает размер одного update, состояние комнаты, общий объём загруженных комнат, число подключений, очередь медленных клиентов, а также объём и число persisted-документов. Неактивные комнаты после сохранения выгружаются. Метаданные не содержат времени сохранения, истории удаления и отдельного идентификатора документа. Запись идёт через временный файл и переименование. Удаление persisted-комнаты увеличивает её поколение и проходит через общую очередь записи, поэтому старое поколение не может создать файлы заново.

### Присутствие

Presence публикуется при движении курсора и повторяется heartbeat каждые 15 секунд; TTL на сервере – 45 секунд, время последнего heartbeat существует только в памяти. Agent сводит окна Review одного пользователя в стабильные presence-ID и отправляет `offline`, когда активных интерфейсов не остаётся. Для старых Agent сервер принимает до восьми presence-ID от одного соединения и удаляет их все при разрыве. Обновления присутствия и участников бронирования передаются снимками.

### Брони, обсуждения и предложения

Брони, комментарии и предложения хранят границы как Yjs `RelativePosition` и дополнительно резервный локатор:

- бронь – исходный список localisation-ключей (`initialKeys`);
- обсуждение и предложение – ключи, смещения внутри строк, выделенный текст и короткий контекст.

Перед полной заменой текста (Git refresh, восстановление истории) сервер обновляет локаторы по живым якорям, а после замены создаёт новые относительные позиции. Бронь получает якоря от первой до последней сохранившейся строки своих ключей; та же процедура при загрузке мигрирует ранее схлопнувшиеся диапазоны. Неоднозначный или исчезнувший диапазон получает явное состояние `orphaned`; если ключи вернутся, повторная замена восстановит бронь. Старый диапазон `0:0` без резервных данных не считается открытым комментарием в начале файла.

Бронь можно изменить на месте (`reservation-update`): исполнителя, примечание и, явно, диапазон. Идентификатор и создатель не меняются. У брони есть `revision`; сервер принимает обновление только при совпадении `expectedRevision`, иначе отвечает `stale` (или `deleted`, если брони нет). Новое состояние собирается и проверяется целиком до записи, включая бюджет метаданных; при ошибке исходная бронь не меняется. Ключи нового диапазона сервер вычисляет из канонического текста и не берёт у клиента. Исполнитель всегда канонизируется по каталогу пользователей. Каждый запрос получает коррелированный ответ `reservation-update-result`; отказ в правах или проверке отображается как ошибка, а исчерпание протокольных лимитов закрывает соединение, как для остальных сообщений. Если операция уже применена, но не удалось записать завершение в журнал аудита, клиент получает `saved`. Поддержка объявляется флагом `reservationUpdates` в `synced`. Изменять и удалять брони может любой участник с правом записи документа – это сознательная политика.

Предложение содержит исходный текст; сервер атомарно применяет замену только при точном совпадении актуального диапазона, иначе помечает предложение `stale`. Принятие сохраняет две роли: `suggestionAuthor*` – создатель предложения, обычные `author*` – принявший. Только принявший получает изменение в своей персональной проекции. Отмена принятой правки – серверная операция: сервер проверяет, что принятый текст не изменился, возвращает исходный диапазон и снова открывает предложение.

### Авторская история и персональные проекции

`DocumentHistory` хранит ограниченную последовательность gzip-снимков текста с публичными метаданными автора и времени. Частые изменения одного автора сворачиваются в сессию; снимки не входят в Yjs и не содержат обсуждений и броней. Сжатие выполняется асинхронно на снимке конкретной ревизии; история сериализуется за один проход, распакованный текст старых снимков освобождается. Восстановление проверяет актуальный `headId`, рассчитывает будущий размер CRDT на копии документа и только затем заменяет текст серверной транзакцией. Оно всегда добавляет новую запись и поэтому обратимо.

Кроме общей рабочей копии история хранит для каждого автора карту изменённых localisation-ключей относительно канонического Git-текста, Git-базу и неразрешённые личные конфликты. Изменение одного ключа несколькими людьми образует набор авторских вариантов и явный конфликт, а не посимвольное смешивание. При смене Git-базы варианты перебазируются трёхсторонним слиянием; правки, уже вошедшие в Git, снимаются с личного слоя. Структурная сигнатура содержит последовательность ключей и неключевых строк, поэтому пустые строки и комментарии не теряют положение. Обычная правка значения одного ключа идёт по быстрому построчному пути, а структурные правки и дубли ключей – через полный анализатор.

По запросу `personal-projection-get` сервер строит проекцию `Git HEAD + изменения выбранного автора` с хеш-ревизией и передаёт её дельтами с проверкой базовой ревизии; при рассинхронизации отправляется полный снимок. В конфликты проекции попадают только пересечения, в которых участвует выбранный автор. Кэш проекций ограничен для каждого соединения; чтение неизменной проекции не вызывает записи.

### Канонический Git

`git-branch-cache.mjs` держит shallow sparse-клоны активных веток публичного репозитория, включающие только `localisation/russian`, `localisation/english` и `localisation/replace`. Обычная комната инициализируется серверным Git-текстом, хранит commit и базовый текст в метаданных и при обновлении ветки выполняет трёхстороннее объединение `прежняя Git-база / совместный текст / новая Git-база`. Независимые ключи объединяются автоматически; совпавшие конфликты Review разрешает по одному ключу в локальном diff.

Agent передаёт полный локальный `HEAD` и blob открытого файла. Несовпадение вершины без изменения файла даёт предупреждение, но комната остаётся доступной для записи; несовпадение blob блокирует только этот файл. Список изменений вычисляется за весь диапазон от локального `HEAD` до канонической вершины, поэтому пропущенные коммиты не теряют затронутые файлы, а коммиты вне localisation-папок не блокируют комнаты. Canonical Git refresh проходит через ту же очередь, что и тикетные операции.

### Тикеты

`TicketStore` хранит метаданные тикетов отдельно от комнат: название, описание, базовую ветку, полный commit SHA, файлы, участников и статус. Документ тикета использует namespace `ticket-<uuid>:<relative-path>`, поэтому presence, брони, обсуждения и предложения изолируются без отдельной реализации. Начальная версия извлекается Agent через `git show <base-commit>:<path>`; тикет не материализуется в worktree. Каталог тикетов имеет непрозрачную ревизию: сервер уведомляет подключённые комнаты, а Review проверяет ревизию раз в 15 секунд, при возврате фокуса и после подключения.

`TicketService` проверяет хеши тикетных и основных комнат, применяет рассчитанный Agent результат, обновляет базу и физически удаляет тикетные комнаты с историей. Apply и rebase ставят барьеры на очереди всех участвующих комнат и повторно проверяют хеши и состояние; rebase проверяет принадлежность commit ветке до замены текста. `TicketWorkflow` в Agent объединяет базовый Git-текст, совместную основную версию и локальный файл трёхсторонним merge; конфликт любого ключа останавливает операцию до записи и переводит тикет в `git_conflict`. Успешное применение не создаёт Git-коммит.

В production `GitCommitVerifier` через GitHub Compare API проверяет, что базовый SHA существует и является предком выбранной ветки `EaW-Team/equestria_dev` (таймаут 8 секунд, часовой ограниченный кэш, отказ при недоступности GitHub). Переменная `EAW_HUB_GITHUB_REPOSITORY` меняет репозиторий; её отсутствие отключает проверку для лаборатории и тестов.

### Авторизация, роли и аудит

Сервер по умолчанию требует авторизацию. Роли аддитивны: `admin`, `senior translator`, `translator`, `trainee-translator`, `translation-editor`, `mod-contributor`. Права на документ определяет только учётная запись, а не содержимое: `mod-contributor` без переводческой роли редактирует только английские файлы и не принимает решений по предложениям (`packages/shared/src/document-permissions.mts`).

Схема авторизации 5 хранит `enabled` отдельно от существования пользователя. Пароль хранится только как индивидуально посоленный scrypt-хеш (`N=131072`, `r=8`, `p=1`, 32 байта). До scrypt действуют краткоживущие token-bucket лимиты по аккаунту и HMAC источника, а очередь password jobs – глобальный аварийный предел; счётчики существуют только в памяти и не содержат IP. Одноразовый bootstrap-код создаёт первого администратора. При регистрации выдаётся один 256-битный код восстановления с контрольной суммой: в `auth.json` хранится HMAC-SHA-256, а `recovery-pepper.key` входит в зашифрованную резервную копию. Выдача двухфазная: код активируется лишь после подтверждённой записи файла.

`auth.json` содержит отображаемые имена, роли и проверочные хеши паролей, кодов восстановления, сессий и приглашений. IP, User-Agent, имя устройства и время входа не собираются. Отключение удаляет сессии пользователя и исключает его из каталога, но сохраняет учётную запись; безвозвратное удаление дополнительно анонимизирует ссылки в комнатах и истории. Приглашения хранят только хеш секрета, роли, лимит, число использований, срок и флаг отзыва; статусы `active|expired|exhausted|revoked` вычисляются. Временный пароль отзывает все сессии и не допускается к документам до смены.

Обычный bearer-токен администратора не принимается маршрутами управления. `AdminSessionStore` держит в памяти хеши десятиминутных management-сессий для `admin` и `senior translator`, привязанных к исходной сессии и выдаваемых после повторной проверки пароля; изменение доступа требует сессии не старше двух минут. Политика (`management-policy.mjs`) запрещает senior управлять собой, администраторами и ролью `admin`. Экспорт и расписание резервных копий требуют `admin`; долговременное расписание использует отдельный persisted-токен с единственным разрешением на экспорт.

`audit-log.mjs` сохраняет независимые записи в `/data/audit`: подтверждённую личность, время, действие, объект и результат. Удаление сначала фиксирует намерение, затем результат с тем же ID операции. Сбой записи останавливает последующие аудируемые операции до исправления хранилища. Журнал доступен только администратору через `/api/admin/audit` и EaW Hub Admin; пароли, токены и коды восстановления в него не попадают.

При парольной схеме пароль кратковременно присутствует в памяти клиента и сервера и передаётся внутри TLS. Гарантия относится к отсутствию пароля на диске и в журналах и к невозможности восстановить его из хеша. Сервер не печатает секреты в stdout, Caddy не ведёт access log.

### Развёртывание и резервные копии

Docker-контейнер работает непривилегированным пользователем с read-only root filesystem, лимитом 384 МБ и постоянным volume `/data`. Опциональный Caddy завершает TLS; если порт 443 занят, используется существующий reverse proxy. Административный экспорт сначала сбрасывает загруженные комнаты на диск и отдаёт только `auth.json` и `documents`; клиентский скрипт шифрует архив AES-256-GCM. Восстановление сохраняет прежнее состояние в `.before-restore-*`.

Отдельный Windows-deployer собирает минимальный серверный пакет без runtime-данных системным `tar.exe` Windows, подключается по SSH/SFTP с закреплённым host key, проверяет SHA-256 загруженного архива и обновляет Compose-проект. Перед заменой сохраняется откатная копия кода; неуспешная сборка, запуск или `/health` возвращают предыдущую версию. Volume, `.env` и каталог внешних резервных копий не заменяются.

## Desktop Agent

### Локальная граница

Статические ресурсы Review и WebSocket доступны только на `127.0.0.1`. Случайные порт и capability-token создаются один раз для state-каталога и сохраняются с правами текущего пользователя, поэтому открытое окно переподключается после перезапуска Agent. HTTP API требует bearer-токен, WebSocket – точные токен и `Origin`; WebView2 запрещает внешнюю навигацию, новые окна и разрешения. Локальный IPC блокирует сообщения до handshake `ipcChallenge → hello → agentHello` и очищает исходящую очередь при каждом подтверждённом challenge. Единственный WebSocket Review → Agent мультиплексирует логические сессии вкладок.

Окно Agent регистрирует аккаунт по приглашению или выполняет вход по имени и паролю. Пароль не сохраняется; токен хранится как Generic Credential текущего пользователя Windows и передаётся дочернему процессу только через окружение. Удалённые пароль и токен передаются только через TLS; GUI отказывается работать с удалённым `ws://`.

### Привязка документа

Один Agent обслуживает одну локальную копию репозитория и принимает `.yml` из `localisation/russian`, `localisation/english` и `localisation/replace`, проверяя реальное нахождение файла внутри репозитория. Жизненный цикл файла держит `DocumentBinding`; разбор серверных сообщений (`document-server-messages.mjs`), команды броней и обсуждений (`document-actions.mjs`), представление для Review (`document-view.mjs`), доставка и flush (`document-delivery.mts`), дисковое согласование (`disk-reconciliation.mjs`) и персональная проекция (`personal-document.mjs`) вынесены в отдельные модули. Готовность документа привязана к поколению открытого буфера; преждевременные или запоздалые сообщения отбрасываются.

При закрытии последней вкладки Agent запрашивает у сервера `sync-flush`; неподтверждённое локальное состояние остаётся в state-каталоге и отправляется при следующем подключении. Agent строит контрольные точки UTF-8/UTF-16 один раз на снимок, проверяет метаданные файла до чтения и не перекодирует неизменные снимки обсуждений и броней.

### Персональная материализация

`review-server.mjs` записывает в настоящий файл репозитория персональную версию пользователя; удалённые Yjs-обновления меняют общую модель и метаданные, но не записывают чужой текст в worktree. Режим материализации (`mine` или чистый `git`) хранится вне репозитория с привязкой к репозиторию, ветке и пути. Для каждого ключа, которым общая версия отличается от Git HEAD, Agent вычисляет состояние `included|excluded|custom`; выбор заменяет только указанный ключ и не создаёт Yjs-обновления.

Запись требует готовой непротиворечивой личной версии и актуального Git blob. Перед записью Agent канонизирует путь, проверяет containment и совпадение identity открытого handle с файлом, сверяет файл с последней прочитанной базой, затем пишет и синхронизирует временный соседний файл и атомарно заменяет исходный. Полностью совпадающий файл не перезаписывается; ошибка замены не усекает исходный файл. При внешнем конфликте или смене workspace запись приостанавливается.

Внутреннее представление текста нормализуется к LF: дисковая база, ожидаемый результат записи и `localFileText()` сравниваются в LF. Физический формат worktree восстанавливается при записи; для нового файла ожидаемый EOL определяется по `.gitattributes`, `core.autocrlf` и `core.eol` без запуска clean/smudge-фильтров. Сырой серверный текст не нормализуется: UTF-8 byte patches применяются к исходному снимку, иначе CRLF сдвинул бы позиции.

### Дисковое согласование

Для каждого сочетания `репозиторий + workspace + путь` Agent хранит подтверждённую базу слияния в state-каталоге (`%LOCALAPPDATA%\EaWLocalisationHub`), а не в worktree. При внешнем изменении сравниваются `последний подтверждённый персональный файл / общая версия / новая версия с диска`; из одной базы вычисляются общий результат для CRDT и персональный для worktree. Разные ключи объединяются с авторством операции; ключ, уже изменённый другим автором, сохраняется отдельным вариантом и требует явного выбора. Повреждённая или отсутствующая база не приводит к молчаливому выбору стороны. Новая база записывается только после фактической материализации. Конфликты имеют источник `disk` или `canonical`, и разрешение маршрутизируется в соответствующий обработчик.

### Git на стороне Agent

`git-executable.mts` централизует все локальные Git-вызовы и на Windows находит как системный Git, так и Git из GitHub Desktop. Workspace определяется текущей веткой (`git branch --show-current`); ручного выбора в GUI нет, `--workspace` остаётся инструментом лаборатории. Переход на новую ветку запускается только после двух последовательных одинаковых наблюдений; отсутствующий результат считается временной ошибкой. При смене ветки Agent замораживает клиентов, дожидается исчезновения `index.lock` и стабильности `HEAD`/index, сохраняет несохранённый буфер прежней ветки в `git-recovery`, переподключает комнаты, а Review остаётся read-only до нового `documentReady`.

`git-file-history.mts` выполняет только локальные Git-команды с массивом аргументов и проверенным путём, следует переименованиям и отдаёт историю файла страницами. Monaco Diff Editor вычисляет визуальное сравнение на клиенте; сервер в этом не участвует.

`repository-sync.mjs` – opt-in сервис авто-fetch и fast-forward текущей ветки. Настройки хранятся вне worktree в `state/repository-sync/<sha256>/settings.json`; по умолчанию всё выключено. Используется upstream текущей ветки; ветки без upstream и detached HEAD не обновляются, Git не запрашивает пароль интерактивно. Fetch адресует только remote-tracking ref, обновление – fast-forward на полученный commit. Перед ним проверяются изменения worktree и индекса, расхождение веток, незавершённые операции Git, конфликты Review и неподтверждённые проекции; guard приостанавливает материализацию, дожидается durable flush каждой комнаты и повторно проверяет ветку, HEAD и upstream. Новый ввод в период ожидания отменяет checkout. Checkout имеет таймаут 30 секунд и отключает hooks и submodule recursion. Reset, stash, rebase, merge-коммиты, commit и push сервис не выполняет. Review обращается к сервису через `/api/repository-sync`: GET только читает статус, POST требует подтверждения и точной идентичности показанного checkout.

### Локальные индексы и кэши

`diff-cache.mjs` хранит сжатые JSON-снимки дорогих представлений: неизменяемых версий истории, Git history diff, файлового diff тикета и сверки локализации. Имя файла – SHA-256 от пространства имён и ключа; ключ включает все входы (HEAD, хеш текста, хеши обоих языковых файлов), поэтому кэш не является источником истины. Файлы создаются с правами `0600` и атомарным переименованием; пределы – 256 МиБ, 512 записей и 64 МиБ несжатого JSON на запись, вытеснение по времени последнего чтения.

Индекс ключей строится в отдельном worker thread (`localisation-key-index-worker.mjs`). Ключи группируются по языку файла (суффикс `_l_<язык>`, папка или заголовок) и передаются один раз в `languages.<язык>.keys`; файлы без определимого языка игра не загружает, поэтому их ключи не индексируются. Индекс также содержит структурно разобранные объявления `defined_text` из `common/scripted_localisation` и, при наличии, имена getters из документации установленной HOI4 (`EAW_HOI4_DIRECTORY` или стандартный путь Steam); этот список не является исчерпывающим whitelist. Неизменённые файлы берутся из кэша по размеру и времени изменения. Изменение индекса определяется по отпечатку входов (stat файлов и документации), а не сериализацией всего результата; неизменный индекс не копируется из worker, а HTTP отвечает `304`. При превышении лимитов индекс помечается неполным, и Review не делает выводов об отсутствующих ключах.

`/api/localisation-file-diagnostics` читает байты локального файла (bearer-токен, проверка containment и identity handle, предел 16 МиБ) и сообщает об отсутствии UTF-8 BOM и некорректном UTF-8. Анализ никогда не переписывает файл.

### Обновление клиента

Проверки при запуске, по таймеру и при несовместимости протокола только читают метаданные GitHub Releases. Скачивание и установка запускаются только кнопкой «Обновить клиент…» с подтверждением; обработчик передаёт `-Install` отдельному процессу PowerShell, окно которого не зависит от остановленного Agent. Скачивание потоковое с прогрессом; проверка SHA-256, установка и перезапуск показываются отдельными этапами. Успех фиксируется только после появления нового процесса Agent нужной версии и его файла обнаружения Review.

## Review

### Окно и вкладки

Окно содержит общий менеджер вкладок и отдельный same-origin iframe с редактором для каждого «тёплого» документа. Контроллеры Monaco, CRDT, undo, обсуждений и материализации изолированы; идентичность вкладки включает абсолютный путь и тикет. Только активная сессия публикует курсор и присутствие. Проверки Git видят все тёплые сессии.

Чистая неактивная вкладка засыпает через 5 минут (настройка 1/5/10/15/30), мягкий лимит тёплых редакторов – 4/8/12/20. Черновики, локальная undo-история, открытые диалоги и формы (включая форму изменения брони), незавершённая доставка, конфликты и материализация препятствуют усыплению. Спящая вкладка сохраняет позицию и прокрутку и при открытии получает актуальный документ; после перезапуска окна сохранённые вкладки загружаются лениво.

### Документ и режимы ввода

`review-document.ts` хранит браузерную CRDT-копию, применяет отдельные изменения Monaco без повторного сравнения всего документа и повторяет состояние при переподключении. Agent принимает обновления с происхождением конкретного Review-клиента, поэтому персональный undo сохраняет прежнюю модель. Команды выделения передают относительные якоря Yjs, а изменившийся исходный текст предложения требует повторного действия пользователя. Документ не инициализируется до готовности исходной персональной проекции.

В режиме «Правки» клиент вычисляет одну локальную вставку, замену или удаление, возвращает редактор к каноническому тексту и отправляет предложение с UTF-8-границами; исходник меняется только после принятия. Undo удаляет последнее предложение, Redo создаёт его снова; при внешнем изменении текста redo-ветка очищается. Происхождение символов хранится в `Int32Array` с общим бюджетом памяти. Отображение `зачёркнутый оригинал + цветная замена` расширяет многобуквенную замену до границ Unicode-слова; однобуквенные замены, вставки, удаления и пунктуация не расширяются.

### Панель совместной работы

Тонкий координатор `app.ts` связывает модули: применение снимков presence, броней, конфликтов и обсуждений (`collaboration-messages.ts`), левую панель (`collaboration-panel.ts`, `list-items.ts`), форму изменения брони (`reservation-editor.ts`), карточки обсуждений, декорации Monaco, режимы ввода, историю предложений и профиль. Agent обрамляет полные снимки сообщениями `reviewBatchStart`/`reviewBatchEnd`; клиент не отображает промежуточные reset-состояния, объединяет отрисовку в один animation frame и сохраняет DOM неизменившихся элементов по идентификатору и fingerprint.

Форма изменения брони сохраняет введённые данные при ошибке, при устаревшей ревизии предлагает загрузить актуальную бронь и ждёт подтверждения сервера не дольше 15 секунд. Ключи выбранного диапазона считаются общим браузер-безопасным парсером `localisation-keys.mts`, тем же, что использует сервер.

Карточки обсуждений размещаются напротив связанных строк с разрешением вертикальных коллизий. Навигация вычисляет все комментарии и правки под позицией, выбирает самый узкий диапазон и прокручивает колонку к карточке; повторное нажатие перебирает наложенные сущности. Аватар обрабатывается через Canvas (квадрат 96×96, WebP без метаданных); сервер принимает не более 16 КиБ и проверяет формат.

### Синтаксис и орфография

Синтаксический анализ работает в Web Worker. Он проверяет заголовок языка относительно пути, двоеточие и имя ключа, кавычки, escape-последовательности (`\n`, `\t`, `\N`, `\T`, `\"`, `\\`), ссылки `$KEY$`, цвета `§Y…§!`, иконки `£icon£` и `£$ICON$£`, выражения `[...]`, форматтеры и проценты. Ссылки проверяются только по ключам того же языка; при неполном индексе, неизвестном языке или ошибке загрузчика выводы об отсутствующих ключах не делаются. Семантический слой подсказывает вероятные опечатки getters (только при единственном близком известном имени) и прямые циклы локальных ссылок. Байтовые проверки файла запрашиваются у Agent не чаще раза в 10 секунд на файл. Новые диагностики устанавливаются атомарно, чтобы подчёркивания не мигали.

Орфография: сервер готовит расширенный русский словарь в worker thread и раздаёт базовый Hunspell и компактный Bloom-индекс словоформ, а также общий словарь команды. Проверка видимого фрагмента и подбор вариантов выполняются локальным Web Worker, текст документа на сервер не передаётся. Подчёркивания – декорации без hover; правый клик открывает добавление в словарь и быстрые исправления.

### Сравнения, история и аудит пары

История Hub, Git-история файла, diff тикета и конфликты открываются в Monaco Diff Editor на клиенте с `hideUnchangedRegions`; Agent лениво отдаёт снимки через локальный кэш. Английское окно – тот же Review Host в режиме только чтения; прокрутка синхронизируется через `BroadcastChannel` по ключам локализации. Пакетная замена ключей разделена на разбор (`localisation-replace.mts`) и файловую транзакцию (`key-replacement-workflow.mjs`), применяется по хешам предпросмотра и никогда не передаёт текст оболочке. Сверка RU/EN читает оба файла один раз, сравнивает структуру и ключи, а также (как подсказки) кратности технических вставок и форматтеров без учёта порядка.

### Язык интерфейса

Строки интерфейса пишутся по-русски и переводятся каталогом `packages/shared/locales/en.json` через `uiText(шаблон, ...значения)`; значения (ключи, пути, текст документа) никогда не переводятся. Диагностики синтаксиса передают вместе с готовым русским текстом исходный шаблон и аргументы (`messageTemplate`, `messageArgs`), поэтому Review переводит их по шаблону. `uiMessage` с обратным сопоставлением готового текста оставлен только для прочих сообщений Agent, которые ещё не передают шаблон.

## Границы исходного кода

Entrypoint-файлы только связывают подсистемы. `test/architecture.test.mjs` проверяет наличие выделенных модулей и ограничивает размер координаторов (`main.mjs`, `auth.mjs`, `document-binding.mjs`, `app.ts`, `collaboration-panel.ts`, `review-cards.ts`) числом непробельных символов, а не строк: объединение операторов в одну строку не освобождает место. Если бюджет исчерпан, нужно выносить связный модуль. Это предохранитель от возврата к монолитам, а не метрика качества.
